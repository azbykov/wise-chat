# Vision

Что мы строим, для кого и где проходят границы. Требования заказчика — в [TASK.md](TASK.md),
технические решения — в [ARCHITECTURE.md](ARCHITECTURE.md).

## Что это

Веб-чат один на один с доставкой сообщений в реальном времени и видео-историями на 24 часа.
Это тестовое задание: продукт живёт на машине ревьюера, а оценивают по нему код и инженерные
решения.

## Для кого

| Кто | Что ему нужно |
|---|---|
| **Ревьюер** | Поднять проект одной командой, за пять минут проверить сценарии из критериев успеха, прочитать код без усилий |
| **Интервьюер** | Понятные решения, которые автор может объяснить и защитить |
| **Пользователь чата** (условный) | Зарегистрироваться, найти собеседника, переписываться без перезагрузки страницы, записать историю |

## Принципы

1. **Сначала обязательное.** Ни одна опциональная функция не начинается, пока не закрыты все
   обязательные критерии успеха.
2. **Просто, но правильно.** Минимум движущихся частей, но без дыр: проверка доступа к диалогам,
   хеширование паролей, валидация, понятные ошибки.
3. **Каждое решение объяснимо.** Если решение нельзя коротко обосновать на собеседовании, его здесь
   быть не должно. Компромиссы записаны в ARCHITECTURE.md.
4. **Идиоматично для стека.** Nest-модули, DTO с class-validator, Svelte stores — то, что ревьюер
   ожидает увидеть.
5. **Не выходить за рамки ТЗ.** «Сложная UI/UX не требуется» понимаем буквально: чистый базовый
   интерфейс без лишних функций.

## Объём

### P0 — обязательно (критерии успеха)

- Регистрация (email, password, username), вход по JWT, закрытые роуты на фронтенде и бэкенде
- Список всех пользователей и поиск по username, кнопка «написать»
- Создание диалога один на один (повторно с тем же человеком не создаётся)
- Список своих диалогов с последним сообщением, отсортированный по активности
- Отправка текстовых сообщений и их получение через WebSocket без перезагрузки
- Валидация входящих данных, единый формат ошибок, состояния loading и error в интерфейсе
- Надёжная отправка:
  - сообщение показывается сразу со статусом `sending`, затем `sent` или `failed`, у `failed` —
    кнопка «повторить». Это и есть состояния loading и error для отправки, которые требует ТЗ;
  - повтор не создаёт дубль: `clientMessageId` с уникальным индексом.
- Доставка без потерь:
  - у каждого сообщения номер `seq` внутри диалога, без пропусков. Сообщение, номер и превью
    диалога пишутся одной транзакцией;
  - клиент замечает пропуск в номерах и догружает недостающее;
  - после переподключения сокета догружается всё пропущенное. Иначе сообщения, пришедшие во
    время обрыва, не появятся без перезагрузки, а это нарушает критерий «сообщения приходят без
    перезагрузки страницы».
- README с инструкцией по запуску

Надёжная отправка и доставка в P0, а не в P1, потому что от них зависят модель данных (`seq`,
replica set ради транзакций), API (`clientMessageId` в `message:send`, курсоры `before` и
`after` по `seq`) и store `messages`. Добавлять их потом означало бы переделывать уже готовое.

### P1 — «будет плюсом» из ТЗ и дешёвое

- Docker Compose: `docker compose up` поднимает весь проект
- Тесты: unit и e2e на бэкенде, unit на stores фронтенда
- Автоматическая повторная отправка сообщений в статусе `failed` после переподключения (в P0
  повтор только по кнопке)
- Счётчик непрочитанных: бейдж у диалога в списке, растёт с новыми сообщениями, сбрасывается,
  когда диалог открыт, во всех вкладках сразу. В ТЗ его нет, но без него список диалогов не
  показывает, где новое. Всё, что для него нужно на сервере (транзакции, `seq`), уже есть в P0.

### P2 — «будет плюсом», дорогое

- Stories: запись с веб-камеры до 15 секунд, лента пользователей с активными историями, просмотр,
  автоудаление через 24 часа

## Не делаем

Исключено заданием:

- групповые чаты, файлы и изображения в чате, редактирование и удаление сообщений;
- фильтры, обработка, конвертация и оптимизация видео;
- push-уведомления, деплой в продакшн, сложный UI/UX.

Исключено нами сознательно, чтобы не усложнять:

- горизонтальное масштабирование: несколько реплик, балансировщик, адаптер Socket.io и
  transactional outbox, который понадобится для доставки при нескольких репликах;
- индикатор «печатает», отметки о прочтении у собеседника («галочки»), онлайн-статус;
- общий пакет схем между фронтендом и бэкендом и OpenAPI.

Сначала сюда входили и refresh-токены с ротацией, и e2e-тесты в браузере с CI. В итоге их
сделали: без refresh-токена сессия обрывалась каждые 15 минут, а e2e проверяет сценарий из
раздела ниже одной командой.

Всё это перечислено в README в разделе «Что можно улучшить», чтобы было видно: мы об этом знаем
и сознательно не стали делать.

## Сценарий проверки

Что ревьюер должен суметь сделать за пять минут:

1. `docker compose up --build`, открыть приложение в браузере.
2. Зарегистрировать Алису в обычном окне и Боба в приватном.
3. Алиса находит Боба поиском и открывает диалог.
4. Сообщения идут в обе стороны мгновенно. У Боба новый диалог появляется в списке без
   перезагрузки. (P1) Пока у Боба открыт другой экран, у диалога растёт счётчик непрочитанных;
   Боб открывает диалог — счётчик сбрасывается.
5. Перезагрузка страницы не теряет ни сессию, ни историю. Если остановить бэкенд и запустить
   снова (`docker compose restart api`), сообщения, пришедшие за это время, догружаются без
   перезагрузки страницы. Свои сообщения, отправленные во время обрыва, становятся `failed` и
   уходят по кнопке «повторить» без дублей; (P1) после переподключения — автоматически.
6. Невалидные данные при регистрации, занятый email и неверный пароль дают понятную ошибку.
7. (P2) Алиса записывает историю, Боб видит её в ленте и смотрит.

## Готово, когда

**Определение готовности — P0 и P1 целиком.** Docker Compose и тесты в ТЗ опциональны, но мы
включаем их в готовность: они стоят недорого, а ревьюер с ними проверяет проект одной командой.
P2 (stories) в определение готовности не входит. Если stories сделаны, они проверяются шагом 7
сценария.

- Все обязательные критерии успеха из TASK.md проверены по шагам 1–6 сценария выше.
- `docker compose up` на чистой машине поднимает проект без ручных шагов.
- `pnpm test` зелёный, `pnpm lint` и `pnpm typecheck` чистые.
- README описывает запуск, архитектуру, решения и ограничения.
